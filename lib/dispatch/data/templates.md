人读单一载体：跑批的规则正文只在这里维护。注入块里的 `{templates}` 指到本文件的绝对路径，

## 方案文档规范

读者定位（裁冗余的尺）：方案只给当下跑批的角色看——用户（白话导读）、施工 subagent（落点）、复核 subagent（现状证据＝攻击靶子，证伪门各形态另拿冻结方案当判据）、主会话自验（验收命令）；不为考古读者写背景铺垫，考古归 git log 与 commit 正文。

主会话亲写方案文档（本工作区的落点是 `/home/nvse/code/实施方案/`），骨架按四节：

### 零、白话导读
给用户两段：①总批白话三五句——这轮大概做什么、为什么现在不行（说全貌，不展开做法）；②关键取舍的人话版——决策表里影响理解的自决项各配一句人话（例：为什么用 A 不用 B、某个术语是什么意思），用户不用去搜。全文不出现函数名/文件路径/表名。每批（单批也要）开头批白话：该批具体怎么做的——解决逻辑是什么、按什么顺序动哪几块，配上取舍（选了什么、丢了什么、为什么这么选），写成用户读完就能判断「这个做法合不合理」的样子，篇幅按取舍多少来。用户只读白话段也能拍板与质疑，其余各节是给施工与复核的工程细节。

### 一、现状与差距
承重事实两三段：现有结构在哪、为什么不够、缺口是缺保证还是缺零件；每条带 file:line 证据；病根归类——哪几件症状是同一个病的补偿零件，哪几件看着像病其实各管一层。判错结构的方案后段全歪，这里写死。排除性事实（「已核无 X」类）只记承重项——缺了它病根判定就不成立的那几条；非承重的全量自证清单不写。

### 二、方案与落点（按批分组）
先给设计决策表：选项/推荐/理由三列（选项列有真选项才填，无选项行只给推荐/理由）；已拍板的标注拍板来源（用户原话短引＋会话 ref 或记忆条目名）；表内不再单列「待拍板节」，未决项在表中标「待拍板」。理由列只写一句核心依据（拍板来源的用户原话短引不计入），取舍的展开论述归白话导读——同一取舍不在两处各写一遍。再按批分组：每批一个子节＝批标题＋落点逐文件一行（文件＋改什么，禁无主的「某处/相关模块」）＋该批验收命令（可粘贴执行、预期明确）＋变异要求（改锚点必红、红后复原）。落点默认**描述级**：给 file:line 锚点＋改什么语义，标准是施工者无需做任何设计决策；措辞即语义的落点（用户可见文案、注释里的 why）可给成品句照抄，其余不贴成品代码。跨文件绑死关系（落 A 必同步 B）单列「绑死关系」清单逐条点名（A↔B＋校验它的机械门名）——清单缺项或互验不落在机械门上＝方案未收口。无中间过渡态：依赖零件与本批同攒一批上线时，不留兼容分支不造过渡件，按终态直写。确需跑了才知道的面在二节末尾单列「未看面」逐条点名（怎么暴露、谁跑），不点名的面按已看全论。

### 三、风险
真风险与对策：最可能坏在哪、怎么防/怎么退；不可逆操作单列；无则写「无」。

### 定稿自查（四条，逐条过）
1. 白话导读：无代码标识符；总批＋每批各有白话段，批白话含该批关键取舍的人话版；用户不搜术语能懂、能据此质疑方案。
2. 现状与差距：每条给了 file:line 证据；病根归类清楚（同病补偿件归堆、非病灶说明各管哪层）；推不出缺口的「候选差距」已删。
3. 方案与落点：多批按批分组、单批直给；逐文件可执行，缺文件＝方案没做完；每批验收命令粘贴即跑；互验点都点名且落在机械门上；决策表已拍板项有来源；无中间过渡态（依赖零件同批上线则按终态直写）；决策表理由不与白话导读重复展开。
4. 风险：不可逆操作单列；对策可执行；无则写「无」。

过目：交用户过目，认可再施工；必要处配改前/改后例子对比（过目对比只进对话，不写进方案文档）。方案的改与不改按施工划线：证伪 findings、过目意见、拍板来源都在这之前回写进方案（施工方照着干、用户照着看），拍板后到派出施工之间的调整照样改方案；派出施工 subagent 起冻结——施工与证伪门期间发现的偏差、补行漏项只改代码与测试，在 commit 正文与台账留痕，不回写方案（证伪门拿冻结版当判据，回写＝把判据改成结论，门就空了）。

## 方案证伪 brief（施工前，对象＝方案文档）

派发纪律（本段逐字执行）：
- 按词表选形：保底形（第一性原理＋砍刀）每批必派，其余按「复核形态词表」触发列选——改了什么派什么；每形一只只读 subagent，多只一次 workflow 编排并行。
- 派出即冻结：方案文档在证伪者工作期间不再编辑；确要改先等回执或召回重派，否则证伪者读旧版交过期 findings。
- 裁决后分流：裁决引入新机制/新结构的，新机制面补一轮定向证伪（一轮为限）；只改锚点/行号/命令名的直接进下一阶段；全量复核只在方案整体重写时。
- findings 附 file:line 或方案段落原文＋可复跑命令（能跑则跑）；只报问题不附方案大段，根治法归主会话；答不上按「转派」。
- 一轮为限，报完即收。

### 设计七维清单（设计七维/设计七维·终审共用）
①机制选型——更正规的现成机制被绕过？是否已在打第二个补丁＝该停下重写该块；②结构职责——单一职责、依赖方向无倒挂、改动长进原有结构；③单一真相源——常量/类型/文案/配置无第二处定义、写通道唯一；④契约完备——接口显式、错误分类覆盖全部失败路径、时序边界有交代；⑤演进性——此改法让下次同类需求更容易还是更难，有无「以后必须返工」的雷；⑥同型面——同模式点全仓还有哪，该一起改的列出；⑦规范对齐——与项目既有模式一致。下探一层：不止审改动本身，还审改动所坐的底层机制——地基歪就报「底层重整」。

## 证伪门 brief（提交前，对象＝净 diff）

总纪律（每份 brief 首行）：只拿方案文档与净 diff（不读施工汇报），按方案文档自己重跑验收命令与机械门，独立重算后只报问题。

派发纪律（本段逐字执行）：
- 按词表选形：保底形（砍刀·diff＋连带面）每批必派，其余按「复核形态词表」触发列选——改了什么派什么；每形一只只读 subagent，多只一次 workflow 编排并行。
- 不采信施工者「已通过」的陈述：自己跑方案文档里的验收命令与机械门，贴出命令与实测输出。
- findings 每条附可复跑命令（file:line＋命令原文＋实测输出），没有复跑命令的条目不算证据。
- 只报问题不附方案；无法判断的按「转派」而不是硬答。
- 一轮为限：本轮报完即收，不追加重派；余留交主会话裁决。
- 施工段标记口径：判的是「哪个施工段」的净 diff，段外发现单列、不混进本段结论。
- 变异复原只许 sed 改回字符串，禁 git checkout/restore——净 diff 阶段工作树带着整批未提交改动，整文件回滚会连批一起抹掉。

## 横切判据

本段逐条执行，不看懂的条目按「转派」处理：
- 阈值标定：每个魔法数是否带来源（官方文档/实测/业务规则）？来源站得住吗？
- 断言判别力：新增的守门断言改坏锚点是否必红（变异测试）？判别力不足的断言等于没有。
- 缺省放行：参数缺省时最该拒的真的拒了吗（缺省值放行的恰是最该拦的请求）？
- 部分失败显式：多产物流程失败时留下的产物是否显式报错，而不是静默半成品？
- 设计四信号：按 AGENTS.md 设计纪律的四个自检信号，任一命中即为设计级 finding。
